แหล่งข้อมูลแต่ละเจ้าให้ความแม่นไม่เท่ากัน และบางเจ้าไม่ให้อะไรเลย ถ้า design ระบบโดยไม่แยกสามอย่างนี้ จอจะแสดงตัวเลขเดาปนตัวเลขจริงโดยที่คนมองแยกไม่ออก ซึ่งแย่กว่าไม่มีจอ ข่าวดีคือ Claude มีไฟล์ที่เก็บ % จริงไว้ให้อยู่แล้ว — เพิ่งเจอตอนสำรวจเครื่อง และมันเปลี่ยนแผนไปเยอะ

กติกาข้อแรกของระบบ

ทุกตัวเลขติดป้ายความน่าเชื่อถือ และป้ายนี้ห้ามซ่อน:

reported server บอกมาตรงๆ · derived คำนวณจาก log ที่ครบถ้วน · estimated ประมาณจาก budget ที่ calibrate เอง · calibrating ข้อมูลยังไม่พอ — แสดง token ดิบ ไม่ปลอม %

สิ่งที่จะไม่ทำ

ไม่ scrape หน้าเว็บ claude.ai / chatgpt.com ด้วย headless browser และไม่เรียก private endpoint ที่ไม่ได้ documented เพราะมันเปราะ เสี่ยงผิด ToS และเวลาพังมันพังเงียบ — จอจะโชว์ตัวเลขเมื่อวานต่อไปเรื่อยๆ โดยไม่มีใครรู้

สถาปัตยกรรม

อ่านไฟล์ในเครื่อง แล้ว normalize ให้เหลือรูปเดียว

ข้อมูลต้นทางอยู่บน filesystem ของเครื่องที่รัน CLI — deploy ขึ้น cloud แล้วอ่าน ~/.claude ไม่ได้ ดังนั้นเฟสแรกจึงเป็น local-first แล้วค่อยแตกเป็น collector ทีหลัง

สิ่งที่เจอตอนสำรวจเครื่อง

Claude เก็บ % ไว้ให้แล้ว — แค่ไม่มีใครบอก

แผนเวอร์ชันแรกวางไว้ว่าจะต้องคำนวณ % ของ Claude เองจาก token แล้ว calibrate หา budget ซึ่งเป็นส่วนที่ยากและแม่นน้อยที่สุดทั้งโปรเจกต์ — ไม่ต้องทำแล้ว

Claude desktop app เขียนไฟล์นี้ไว้เองอยู่แล้ว และมันคือสิ่งที่หน้า /usage ในแอปใช้: 

~/Library/Application Support/Claude/plan-usage-history.json

{ "version": 2,
  "samples": [
    { "t":   1788230844516,        // epoch ms — เขียนทุก ~15 นาที
      "org": "f99b3e24-…",         // UUID ของ account → ใช้แยก 2 accounts ได้เลย
      "u": { "fh": 74,             // % หน้าต่าง 5 ชั่วโมง
             "sd": 57,             // % หน้าต่าง 7 วัน
             "xu": 100 } }         // โควตา extra usage
  ] }

สิ่งที่ยืนยันแล้วจากไฟล์จริงบนเครื่องคุณ:

  • 1,851 samples ย้อนหลัง 30 วัน (2 ส.ค. → 1 ก.ย.) — dashboard มีกราฟประวัติใช้ได้ตั้งแต่วันแรก ไม่ต้องรอสะสมข้อมูล
  • จับจังหวะรีเซ็ตได้ — พบ fh ตกจากค่าสูงลงมา 0 ทั้งหมด 8 ครั้งใน 30 วัน → ใช้ derive resetsAt ได้ (ไฟล์ไม่ได้บอกเวลารีเซ็ตมาตรงๆ)
  • sd เคยขึ้นถึง 93% และ fh ถึง 100% → สเกลเป็น 0–100 จริง ไม่ใช่ค่าอื่น
  • เขียนเฉพาะตอนแอปเปิดอยู่ → ถ้า mtime เก่ากว่า 30 นาที ต้อง mark stale

ผลคือ ทั้ง Claude และ Codex ให้ตัวเลข reported ได้ทั้งคู่ ส่วน calibration heuristic ที่เคยเป็นแกนหลัก ถูกลดชั้นไปเป็น fallback เผื่อวันที่ schema ของแอปเปลี่ยน (ไฟล์มี version อยู่แล้ว — ตอนนี้ = 2 → เช็คก่อน parse เสมอ)

ส่วน ~/.claude/projects/**/*.jsonl ยังใช้อยู่ แต่เปลี่ยนหน้าที่: เป็นแหล่งของสิ่งที่ไฟล์ข้างบนไม่มี — token แยกตาม model, ต่อ project, และ cost เป็น USD

แต่มีเงื่อนไขหนึ่งข้อ — และมันกระทบคุณโดยตรง

ไฟล์นี้มีเฉพาะ account ที่ใช้ผ่าน desktop app เท่านั้น account ที่คุณเปิดบน browser จะไม่มีข้อมูลใดๆ ให้อ่านเลย

ทางแก้: Claude.app เป็น Electron และ Electron Framework รองรับ --user-data-dir (ตรวจแล้ว) → เปิด instance ที่สองแยก profile ให้ account ที่สอง แล้วมันจะได้ plan-usage-history.json ของตัวเองพร้อม org คนละ UUID

ความเสี่ยงผลกระทบทางรับมือ
Schema ของ log เปลี่ยนadapter พังเงียบ zod validate ทุก record · ถ้า parse ไม่ผ่านเกิน 5% ให้การ์ดขึ้น error ไม่ใช่แสดงเลขผิด

JSONL โตขึ้นเรื่อยๆสแกนช้าลง byte-offset incremental + ยุบข้อมูลเก่ากว่า 90 วันเป็น rollup รายชั่วโมง
